Analyzing write-write conflicts under the context of snapshot isolation

August 30, 2025 · 8 min read


During my internship at MongoDB this summer, I had the opportunity to dive deep into transaction isolation levels. One interesting area I looked into further is how snapshot isolation is implemented and the role write-write conflicts play in it.

What is Snapshot Isolation?

Snapshot isolation is a concurrency control mechanism that provides each transaction with a consistent snapshot of the database at the start of the transaction. This means that a transaction sees the database as it existed at a specific point in time, regardless of concurrent modifications by other transactions. Transactions read from this consistent snapshot and depending on the implementation, write to local memory before commiting all changes to the database. This is a form of optimistic concurrency control (no locking involved) and so it offers an attractive tradeoff between application safety and performance.

The Lost Update Anomaly

The key properties of snapshot isolation are:

  • Read consistency - All reads within a transaction see the same snapshot
  • No dirty reads - Transactions never see uncommitted changes
  • No lost updates - Concurrent writes to the same data are detected

Write-Write Conflicts in Practice

When two transactions attempt to modify the same document in MongoDB, the system must decide how to handle this conflict. Under snapshot isolation, MongoDB uses a "first-committer-wins" rule: the first transaction to commit succeeds, while the second transaction is aborted with a write conflict error.

Consider this example with two concurrent transactions: 

Transaction T1:                    Transaction T2:
BEGIN                              BEGIN
READ balance = $100               READ balance = $100
UPDATE balance = $150              UPDATE balance = $200
COMMIT (succeeds)                  COMMIT (fails - write conflict)

Alternative Approaches to Conflict Resolution

While researching this topic, I explored several alternative definitions and implementations of snapshot isolation across different database systems:

  • Optimistic concurrency control - Validate at commit time
  • Multi-version concurrency control (MVCC) - Maintain multiple versions of data
  • Timestamp ordering - Use timestamps to order conflicting operations

Implications for Application Design

Understanding these isolation levels is crucial for building robust distributed applications. Developers need to:

  • Design for retry logic when conflicts occur
  • Consider using application-level locking for critical sections
  • Choose appropriate isolation levels based on consistency requirements
  • Understand the trade-offs between consistency and performance

Future Research Directions

This work has opened up several interesting research questions that I'm excited to explore further in my PhD: How can we provide stronger consistency guarantees without sacrificing performance? Can we develop adaptive isolation levels that adjust based on workload patterns? These are the kinds of problems that make distributed systems research so fascinating.
